---
'meocord': minor
---

A process that loads both of MeoCord's builds, such as jest setup files written in CommonJS beside ES module specs or an ES module bot that uses a CommonJS helper package, now injects the app's own instance into a constructor typed with either build's class. `Translator`, `ThemeCache`, `ExecutionContext`, `CooldownStore`, `MemoryCooldownStore`, `HandlerRegistry` and `ShardContext` are one class object for both builds of a MeoCord version, so `instanceof` on these classes agrees between the builds, as it already does for MeoCord's error classes. MeoCord's other exported classes, such as `Logger`, `RedisCooldownStore` and `MeoCordTestingModule`, stay one per build: MeoCord decides nothing by their identity, and only an app's own `instanceof` across the builds tells them apart. A sharded bot whose memory cooldown store comes from the other build now gets the warning that its per-user and global cooldowns count in each shard alone. Previously a class typed from the other build was given an empty instance (for `Translator`, `ThemeCache`, `ExecutionContext` and `CooldownStore`) or refused at startup with "has no decorator" (for `HandlerRegistry` and `ShardContext`). Two installed versions of MeoCord still keep their classes apart. See https://meocord.dev/docs/4.3/testing.
