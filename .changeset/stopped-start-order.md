A start that `stop()` ends now rejects only once the stop is done with the `onShutdown` hooks of what the start made, and `stop()` resolves after it, on every runtime. Done means the hooks have finished, or `shutdownTimeout` has ended the wait for them. Before, the order came from promise timing: on Node it was usually this one, but on Bun `start()` rejected before the values it made were closed, and on Node too when an `onShutdown` hook awaited anything. Code that awaits `start()` and acts on its rejection now finds what the start made shut down. One start is the exception: one still awaiting a provider's factory when the stop's `shutdownTimeout` wait for it ends. The stop resolves without it, and that start rejects once the factory settles. A `stop()` that an `onShutdown` hook calls while a failed start shuts down what it made joins that shutdown, which closes everything in order before the start rejects; the promise the hook gets resolves at once, as for any hook that stops its own app. See https://meocord.dev/docs/4.3/lifecycle-hooks.
