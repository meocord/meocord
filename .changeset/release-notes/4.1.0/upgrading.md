### Upgrading from 4.0

- **What you need.** Node.js 22.13 or later, as 4.0 needed, discord.js 14.27.0 or later and dotenv 18.0.5 or later: `npm install discord.js@^14.27.0 dotenv@^18.0.5`, or the same with your package manager. Most 4.0 bots and their tests build and run without edits. The entries below are what a bot may do differently, or what may now stop it, each with what to check; the [upgrade guide](https://meocord.dev/docs/4.1/migrating#upgrading-from-40-to-41) has the checklist.
- **Class guards cover inherited and autocomplete handlers.** A class-level `@UseGuard` now also guards the handlers a controller inherits, and its `@Autocomplete` handlers, which 4.0 ran unguarded. Check a class guard that reads command-only data or replies on denial: an autocomplete guard has no `reply()`, and a denial closes the menu. See [inherited handlers](https://meocord.dev/docs/4.1/migrating#class-guards-now-cover-inherited-handlers) and [autocomplete handlers](https://meocord.dev/docs/4.1/migrating#class-guards-now-cover-autocomplete-handlers).
- **A base controller's class stages cover its subclasses.** Class-level guards, interceptors, filters and cooldowns on a base controller now apply to the handlers a subclass declares, base first, as global stages wrap controllers. `@Controller({ inheritStages: false })` keeps a subclass to its own stages. See [the upgrade guide](https://meocord.dev/docs/4.1/migrating#a-base-controllers-class-stages-cover-its-subclasses).
- **`applyDecorators(A, B)` applies `B`, then `A`,** as `@A @B` does, so guards combined with it run in the order listed, as do 4.1's interceptors, pipes and filters. 4.0 ran the guards the other way round; list them reversed to keep 4.0's order. See [the upgrade guide](https://meocord.dev/docs/4.1/migrating#applydecorators-applies-its-decorators-in-the-order-they-stack).
- **Message keywords match in any case, and only one handler runs.** `@MessageHandler('hello')` also matches `Hello`, word by word; `caseSensitive: true` keeps the case written. When two patterns match, only the most specific runs, and two handlers with one keyword, which both ran in 4.0, stop the bot at startup. A prefix set in `@MeoCord({ messages: { prefix } })` applies to existing keywords too; give a handler that should match the bare message `{ prefix: false }`. See [the upgrade guide](https://meocord.dev/docs/4.1/migrating#message-keywords-match-in-any-case-and-only-one-runs).
- **Reactions from bots reach no handler,** the bot's own included, as messages from bots never did. Add `{ bots: true }` to a `@ReactionHandler` that should still run for them, and check a count that subtracted the bot's own seeding reactions. See [the upgrade guide](https://meocord.dev/docs/4.1/migrating#reactions-from-bots-reach-no-handler).
- **Duplicate routes stop the bot at startup.** Two component handlers of one type whose patterns match the same customIds, and two handlers of one slash command name, subcommand path or context menu, now stop it with an error naming both, where 4.0 ran one of them by controller order. Two builder classes that build one command, the first of which 4.0 registered with a warning, stop it too. Registering a base controller and a subclass together gives the same error. See [component patterns](https://meocord.dev/docs/4.1/migrating#two-component-handlers-with-the-same-customid-pattern-stop-the-bot) and [commands](https://meocord.dev/docs/4.1/migrating#two-handlers-of-one-command-stop-the-bot).
- **A handler a subclass re-declares on its inherited route takes its own options.** A re-declared `@Command('ping', LoudPingBuilder)` registers its own builder, and a re-declared `@MessageHandler` or `@ReactionHandler` uses its own options, where 4.0 used the base's. To keep the base's, don't re-declare that route. See [the upgrade guide](https://meocord.dev/docs/4.1/migrating#a-re-declared-handler-that-keeps-its-inherited-route-logs-a-warning).
- **Errors after a reply or a deferral are answered.** A deferred reply is edited into the error, and a command that already replied gets a private follow-up, where 4.0 left "thinking…" or sent nothing. An exception filter that handles the error replaces the answer. See [the upgrade guide](https://meocord.dev/docs/4.1/migrating#errors-after-a-reply-or-deferral-are-answered).
- **`Theme` reads the app's theme, with new default colours.** Its colours, and MeoCord's own answers, take MeoCord's new defaults, tuned for contrast on every Discord surface: `Theme.errorColor` reads `#E3606D` where 4.0 had `#DC3545`, and the success, info and warning colours change too. Set `@MeoCord({ theme: { colors } })` to keep 4.0's. See [the upgrade guide](https://meocord.dev/docs/4.1/migrating#theme-is-deprecated-and-its-colours-changed).
- **MeoCord's own metadata keys start with `meocord:`,** so a key of yours such as `'guards'` stays yours. `SetMetadata` refuses only a `meocord:` key and the two keys dependency injection reads, inversify's injectable flag and `design:paramtypes`. Code that read MeoCord's metadata by its string keys reads it with `inspectHandler` from `meocord/testing` instead. See [the upgrade guide](https://meocord.dev/docs/4.1/migrating#setmetadata-refuses-meocords-own-keys).
- **The bot's presence and activities.** MeoCord sets the presence only when `activities` lists some, so a status set elsewhere stays, and it shows them in order from the moment the bot is ready, where 4.0 picked one at random every 10 seconds and cleared the status without any. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).
- **Reactions use the message the bot holds.** MeoCord fetches `reaction.message` only when the bot holds the message by its id alone, where 4.0 fetched it for every reaction. Call `reaction.message.fetch()` where a handler needs data straight from Discord. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).
- **A customId param arrives decoded.** `%2F` and `%25` in a param reach the handler as `/` and `%`; drop a handler's own decoding. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).
- **Logs and exit codes.** `[DEBUG]` lines print only in development, where 4.0 printed them everywhere; set `logLevel` in `meocord.config.ts`, or `MEOCORD_LOG_LEVEL=debug` for one run, to see them elsewhere ([Logging](https://meocord.dev/docs/4.1/configuration#logging)). `Logger` tags `info()` and `verbose()` as `[INFO]` and `[VERBOSE]`, not `[LOG]`, and prints an object as `console.log` does, a small one such as `{ id, name }` on one line, where 4.0 printed one property per line. A SIGINT or SIGTERM after a failed login exits 1, the login's code, where 4.0 exited 0. A token or intent Discord refuses is explained in the log before `start()` rejects, so a 4.0 `main.ts` that logs the rejection prints it again with its stack: skip it there with `if (!isExplainedError(error))`, from `meocord/common`, as a new app's `main.ts` does. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).

### Upgrading builds and the CLI

- **A config option of the wrong type stops `build`, `start` and `register`,** listing every problem, where 4.0 built some silently. An option MeoCord doesn't know is only a warning. See [the upgrade guide](https://meocord.dev/docs/4.1/migrating#a-config-option-of-the-wrong-type-stops-the-cli).
- **A built bot finds its config and assets beside `dist/main.js`,** wherever it starts; 4.0 read the config from the working directory. `.env` is still read from the working directory, so a bot started elsewhere needs its environment set there. Rebuild. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).
- **A production build's config sees `NODE_ENV=production`.** `meocord build --prod` compiles `meocord.config.ts` in production mode, so a config that branches on `NODE_ENV` takes its production branch, and `meocord start --dev` gives the bot `NODE_ENV=development` even when the shell exports `production`, where 4.0 kept the shell's value. On Bun, set `NODE_ENV=production` where you start a production bot yourself, or Bun loads `.env.development` first; the bot warns when it does. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).
- **Builds emit no `eval` devtool.** Development builds use `cheap-module-source-map`, and an `eval-*` devtool set in an `rsbuild` hook is built as its non-eval equivalent, with a warning. A bundle maps its own stack traces to your source; an error tracker that applies uploaded source maps wants `sourceMappedStacks: false`. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).
- **`meocord/eslint` reports a promise nothing awaits,** so `lint` may flag code that passed in 4.0. `await` or `return` it, or mark it `void`. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).
- **The generated rate-limit guard never limited.** Upgrading doesn't change the copy `meocord create` gave a 4.0 app: move its map to module level, or replace it with `@Cooldown`. See [the upgrade guide](https://meocord.dev/docs/4.1/migrating#the-generated-rate-limit-guard-limits).
- **New apps only.** A new app reads every `.env` file and types asset imports; an existing app keeps its own files, and the upgrade guide shows what to copy, along with the `swc` `include` that lets `vitest run --coverage` read an untested file. A 4.0 app created for pnpm adds `reflect-metadata` and `@types/node` to its `devDependencies`, which pnpm needs declared for `lint` and `test`, and on pnpm 11 a `pnpm-workspace.yaml` that sets `@swc/core` and `unrs-resolver` to `false` under `allowBuilds` and lists `meocord` under `minimumReleaseAgeExclude`. On npm 11.16 and later, `"allowScripts": { "@swc/core": false, "fsevents": false, "unrs-resolver": false }` in `package.json` installs without a warning, as a new app's does. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).

### Upgrading your tests

- **Mocks carry ids like Discord's.** An interaction's or message's ids, and `createMockUser().id`, are distinct snowflake strings, so two mocks no longer share a user by default: pass `{ user: first.user }` where a test relied on it. An interaction mock without a `guildId` is a direct message, with `guild` and `member` `null`, and a channel given to `createMockInteraction` or `createMockMessage` sets their `channelId`, `guildId` and `guild`. A member given to `createChatInputOptions` carries its `user` too, so a handler's `User` param gets the `User`, where 4.0 passed the `GuildMember`. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).
- **Typed handler arguments.** A select menu's `values`, `users`, `members`, `roles` and `channels`, and a plain-string customId pattern's params, are checked at compile time, so a declaration that never matched at runtime now fails to compile. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).
- **Messages a test may match.** A refusal MeoCord makes as the app loads starts with what it is on, such as `Class.method:`, so a test that matches a 4.0 refusal's whole text, such as `Invalid pattern …`, needs updating. A `@Command` handler called with the wrong interaction throws a message naming the handler, its decorator and the interaction it takes, where 4.0 said "Invalid interaction type passed to @Command", `createMockInteraction(ModalSubmitInteraction).isFromMessage()` is `true` only when the mock has a `message`, as a real modal's is, and an autocomplete mock's `respond()` rejects more than 25 choices, as Discord does. See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes). See [smaller changes](https://meocord.dev/docs/4.1/migrating#smaller-changes).
- **A suite that relied on an earlier build to supply its `.env`** loads it itself, in the vitest setup or with `dotenv`.
