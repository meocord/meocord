Under `useStrictMocks()`, a mock interaction or message is now on one client with what it holds, as in discord.js: its user, member, channel and server, a message's author and the users it mentions, the channel of an interaction's reply, the users, members, roles and channels an interaction's options or a select menu resolve to, and a user context menu's `targetUser`. A user its options or a select menu resolve to is cached on the mock client it is on unless one with its id is there already, as discord.js keeps the one cached first, and `options.getUser()` still returns the user the test gave; a `targetUser` given is the one cached on the interaction's client. Each takes the `client` given, else the mock client that a message or a message context menu's `targetMessage`, a channel or a guild given to it already holds, in that order, else a new one, so `createMockMessage({ channel })` is on the channel's client. A structure given that is already on another client keeps it. A real `Client` given as `client` is the mock's own client, which caches an interaction's user, server and channel and a `targetUser` given; what the mock holds keeps mock clients of its own, except the server and channel a message makes for itself, and a real `Client` a structure given holds is never taken nor written to. One client means a collector made on `interaction.channel.client`, as `channel.createMessageComponentCollector()` makes one, hears a click on the interaction's reply. Without strict mocks each keeps a client of its own, as before, and code that reads one where strict mocks would give another warns once; the next major version (5.0) shares them without the call. See [Mocks](https://meocord.dev/docs/4.3/mocks).
